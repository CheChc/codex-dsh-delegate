# Codex 规划与验收，dsh 执行

使用 MCP server `dsh` 的 `dsh_run` / `dsh_resume`；客户端可能添加工具名前缀。模型、价格与认证取决于本机 dsh 配置，不能假定某个固定模型。

桥接 v2 提供只读工具 `dsh_bridge_info`；工具已注册时先核对实际版本、路径和默认超时。安装或更新 skill 不会自动更新、重载 MCP 进程，缺少该工具时不能臆造调用。

## 委托选择

委托前先确认三件事：目标是什么；允许读写的范围，以及接口、依赖与不得触碰的边界是什么；怎样算可观察地通过验收。三项清楚且委托有实际收益时，新功能、模块或脚本开发、范围明确的重构、测试修复、数据处理与文档生成都可以交给 dsh；不要求任务机械重复，也不要求 Codex 先写出完整代码。目标或边界仍不清楚时，由 Codex 先读上下文、澄清或给出方案再委托，业务取舍留在 Codex。

方案明确不等于逐行代码已经写好。Codex 交付接口、行为、约束与验收，dsh 选择局部实现细节并编写实现；新增依赖、改变公共接口或架构、扩大范围、降低验收标准，应先报告并由 Codex 判断，不能自行改变方案。已有方案的交互式任务直接用 MCP（`dsh_run`），批处理用 `plan-exec --exec-only` 复用方案，避免再规划一次。

单处极小改动默认可直接完成，不必为了使用工具而拆任务；用户明确指定委托时遵从其选择。研究与文档、笔记类工作先遵守对应领域 skill：Codex 核实来源并作领域判断，dsh 按已定内容规范实现或整理，不自行研究并下结论。

## 1. 先确定方案和边界

- 读取适用的 AGENTS.md、相关源码与已有改动。Codex 决定实现方案和验收标准，dsh 承担明确的实现与修复。
- 按用户已授权的范围推进。不要把“采用委托”本身变成额外确认流程。
- 先记录工作区状态（Git 项目用 `git status --short` 与相应 diff；非 Git 目录用备份或文件快照）。保护用户已有改动。
- 将需求澄清、架构取舍、权限判断保留在 Codex。不要委托凭据处理、生产数据删除等需要主代理直接判断的操作。
- 大批修改与测试修复循环适合分批委托；按依赖、耗时和恢复边界拆批，每批保持可独立验收。

## 2. 检查执行前提

dsh 必须能读取其配置目录并访问配置的模型服务。工具缺失时，说明缺少 dsh MCP，使用[公开 README](https://github.com/CheChc/codex-dsh-delegate#配置-mcp) 的安装指引；不要臆造工具，也不要擅自修改用户全局配置。

遇到 `EPERM open ~/.dsh/...` 或 DNS 错误，先区分沙箱拦截与普通配置、网络故障。明确受当前会话权限限制时，请用户调整为能读取配置且联网的权限（如 Full access）；不要原样重试或改用其他命令绕过限制。不要读取、打印或复制凭据来排障。

用 `dsh_bridge_info` 的 `node_path` 和实际 MCP 环境核对 Node/PATH；dsh 退出码为 0 却没有 JSON 事件仍是协议错误，不能报告成功。

传入绝对 `workdir`，使其包含本批所有允许写入的文件。上层 Codex 有权限不代表下层 dsh 也有权限；无法写入时检查实际 workspace 边界。不要把任务写到其他不相关目录。

## 3. 写出自包含委托

使用 [任务模板](references/task-templates.md)。每次必须包含：

```text
## 目标
完成后的可观察状态
## 涉及文件
逐一列明允许修改的文件
## 具体做法
逐文件说明修改内容、前置条件、边界与保持不变的语义
## 验收
准确的命令、成功条件与应报告的信息
## 禁止
不能修改的内容、未经授权的提交或外部操作
```

- 每次最多修改 5 个文件；超出就分批。读取更多相关文件可以，但写入范围要具体。
- 将足够的上下文、确定的参数与来源随任务传入。dsh 不共享当前对话记忆。
- 新实现优先交付接口、边界和验收标准，让 dsh 生成实现；精确替换用确定性计划。不要把 Codex 先写完代码、dsh 再复制的额外调用误算为节省代码生成额度。复杂任务连续超时后可收敛为已审查补丁，但要如实区分实现与机械执行。
- 使用当前已存在的项目命令，不能为了“通过”而跳过断言、删除测试或伪造结果。
- 批量精确替换应提供原文与替换文，并要求匹配次数或内容哈希符合预期才写入。验证全部前置条件后再开始写；文件系统写入仍可能部分完成，不能宣称整批事务原子性。
- 除非本次授权明确包含它们，禁止自行安装依赖、修改全局设置、提交、推送、发布、发送消息或做破坏性操作。

## 4. 控制批次与时间

- 使用 `dsh_run` 开始明确的一批任务；同一工作目录串行执行，避免重叠写入。v2 对 canonical workdir 使用跨进程锁；它只协调使用该执行器且状态目录一致的调用，不阻止编辑器、其他程序或以不同根目录启动的重叠任务。
- 显式设置 `timeout_sec`，使其短于 MCP 客户端外层超时并留出返回余量。按当前配置决定数值，不把某次环境的限制当成通用上限。
- 将批次缩小到能在预算内完成。超时应先检查状态，不是继续增加时限或原样重跑的理由。
- 可把机械性的“改动 → 运行检查 → 按指定错误修复”合并给 dsh；检查失败涉及方案变化时交回 Codex 判断。

## 5. 主代理独立验收

v2 的工具文本是 JSON。`status=completed` 仅表示 worker 正常结束，`verification_status=not_run` 表示仍需主代理独立验收；失败、超时、协议错误或缺少验收不能报告完成。用结果中的真实 `session_id` 续跑；`usage_samples=null` 表示用量未知，不能当作零费用。

1. 亲自读取实际差异。区分本批变更与先前已有改动，核对范围、语义与遗漏；不能只复述 dsh 的总结。
2. 亲自运行约定的验收命令，保留真实输出与退出码。CLI 正常退出不等于任务完成。
3. 有真实且可信的 session ID 时，用 `dsh_resume` 给出具体失败、期望和剩余范围；没有 ID 就不要猜测，重新组织自包含任务。
4. 连续两轮仍未通过，应重新审查方案、上下文和任务拆分，不再盲目追加同样指令。
5. 完成后汇报实际变更、自己运行的验证命令与真实输出、遗留问题。主代理承担最终质量责任。

## 6. 失败或超时后的恢复

超时、工具断开或没有答复，均不表示“未执行”。dsh 可能已写入部分文件，旧进程也可能仍在工作。

先检查相关进程、差异、文件内容与验证状态；在明确旧任务停止之前，不发起会重叠写入的调用。根据当前状态选取剩余工作，或保留用户改动后恢复本批备份。不要全局回滚、覆盖用户工作或盲目重跑非幂等操作。

v2 从 dsh JSON 事件提取真实 session ID，超时结果会保留已获得的 ID；旧版或尚未收到事件的调用仍可能没有 ID。完整事件和诊断在结果 `log_dir` 下，摘要会裁剪；部分输出和 dsh 的自述都不足以证明修改完成。外层中断后 `running` 记录也可能已过时，应检查实际进程与文件，不能仅凭记录续跑。

无人值守可使用用户已有且已配置的批处理通道。本仓库 `plan-exec` 复用同一执行器；使用明确的 `--file` 范围和 `--verify` 命令。自动提交还需本次授权及 `--commit`，并要求已有目标已跟踪且起始干净，新目标尚不存在且未忽略；拒绝特殊 index 标记和可执行的提交相关 hooks，不通过禁用 hooks 绕过仓库检查。检测到 HEAD 或分支意外变化应报告越界并保留现场；执行失败、验收失败、未验证或范围越界均不得提交。Git 范围检查是执行后的检测，不是文件系统写入隔离。目标项目 `.plan-exec/` 也可能含私有方案和验证输出，建议加入该项目 `.git/info/exclude`；不会自动清理。本 skill 不要求特定机器路径，也不自动安装批处理入口。
